# Сравнение вариантов параллелизации Vedro и рекомендация

Сравниваются четыре плана:
- **01 — asyncio-раннер** (`01-asyncio-parallel-runner.md`)
- **02 — sub-interpreters** (`02-subinterpreters-runner.md`)
- **03 — обёртка над несколькими процессами `vedro run`** (`03-multiprocess-wrapper.md`)
- **03a — плагин-оркестратор подпроцессов** (`03a-plugin-based-subprocess-orchestrator.md`) —
  тот же принцип, что и 03 (несколько процессов `vedro run`), но оркестрация,
  чтение результатов и слияние отчёта реализованы плагином внутри самого
  vedro (через `Registry.ScenarioRunner.register(...)`), а не внешним скриптом

## 1. Критерии сравнения

| Критерий | Почему важен |
|---|---|
| Честный параллелизм по CPU | Даёт ли вариант реальное ускорение на CPU-bound сценариях, а не только на I/O-ожиданиях |
| Изоляция состояния (GIL/глобалы/файлы) | Насколько сильно вариант подвержен проблемам общих глобалов (`StepRecorder`, `Deferrer`, `os.chdir`, `OutputCapturer` и т.п.), описанным в планах 01/02 |
| Объём патчей в самом vedro | Сколько мест в ядре/плагинах нужно патчить или обходить monkey-patch'ем |
| Совместимость с текущим API/версией Python | Работает ли на текущей ветке 1.x без спец. версии интерпретатора |
| Готовность экосистемы / зрелость технологии | Насколько технология стабильна и документирована в CPython/сообществе |
| Сложность реализации (трудозатраты) | Условная оценка объёма работ до рабочего MVP |
| Риск для продакшена | Вероятность падений/некорректных результатов/трудноуловимых багов |
| Накладные расходы (overhead) | Потери на старт, сериализацию, межпроцессный/межинтерпретаторный обмен |
| Live-отчётность / UX вывода | Насколько просто сохранить читаемый прогресс выполнения в реальном времени |
| Совместимость со `Slicer` (межмашинный параллелизм) | Можно ли комбинировать с уже существующим межпроцессным/межмашинным разбиением |
| Влияние на сторонние плагины пользователей | Насколько вероятно, что плагины проекта (не из ядра) сломаются "молча" |

## 2. Таблица сравнения

|---|---|---|---|---|

| Изоляция состояния | ⚠️ Низкая — требует ручного патча всех глобалов (пп. 1–4 плана 01) | ✅ Высокая "по построению" (глобалы автоматически разделены по интерпретаторам), но требует ручной сериализации результатов | ✅ Максимальная — полная изоляция ОС-процессом, патчи ядра не нужны | ✅ Максимальная — та же изоляция процессом, что и 03 |

| Совместимость с Python 1.x/текущей версией | ✅ Работает уже сейчас (3.8+) | 🔴 Требует CPython 3.13+ (публичный API) или нестабильный backport/приватный `_xxsubinterpreters` | ✅ Работает уже сейчас, без ограничений по версии | ✅ Работает уже сейчас, без ограничений по версии |
| Зрелость технологии | ✅ asyncio — давно стабилен | 🔴 Sub-interpreters — экспериментальная, малодокументированная область (риск падений, слабый tooling для отладки) | ✅ `subprocess`/`multiprocessing` — максимально зрелые | ✅ `asyncio.create_subprocess_exec` — зрелый, но собственный NDJSON-протокол и реконструкция результатов — новый код, требующий обкатки |
| Сложность реализации | 🟡 Средняя | 🔴 Высокая | 🟢 Низкая | 🟡 Средняя (партиционирование без дублирования discovery, построчный парсинг NDJSON "на лету", реконструкция `ScenarioResult`/`ExcInfo`, passthrough CLI-аргументов) |
| Риск для продакшена | 🟡 Средний (много точечных патчей = риск регрессий, но локализованы) | 🔴 Высокий (незрелая технология + риск несовместимости C-расширений пользовательских тестов) | 🟢 Низкий (изоляция процессом убирает целый класс багов) | 🟢 Низкий (те же гарантии изоляции, что у 03; единственный доп. риск — деприкация internal API раннера) |
| Overhead | ✅ Минимальный (один процесс, общая память) | 🟡 Средний (создание интерпретатора дешевле процесса, но дороже task'а; сериализация на границах) | 🔴 Наибольший (N полных запусков интерпретатора, повторный импорт конфига/тестов) | 🟡 Тот же overhead процессов, что у 03, но **без дублирования discovery** (выполняется один раз в родителе) — немного ниже, чем у 03 |
| Live-отчётность / UX | 🟡 Нужен отдельный parallel-aware репортер (буферизация вывода на сценарий) | 🔴 Сложнее всего — нет встроенного стриминга между интерпретаторами, нужен свой протокол "тиков" | 🟢 Просто, но вручную — построчная ретрансляция stdout дочерних процессов с префиксом воркера, отдельный от штатных репортеров вывод | ✅ Лучше всех — события ретранслируются в родной `Dispatcher`, штатные репортеры (Rich/Json/PyCharm) работают "из коробки" без адаптации |
| Совместимость со `Slicer` | ✅ Полностью (Slicer работает на уровне scheduler до создания раннера) | ✅ Совместимо (внутри одного процесса можно применить тот же принцип среза) | ✅ Является прямым продолжением/использованием `Slicer` | 🟡 Частично переиспользует стратегию среза `Slicer`, но не сам плагин `Slicer` (партиционирование делает сам оркестратор, передавая явный список файлов, а не флаг `--slice`) |
| Риск для сторонних плагинов пользователей | 🔴 Высокий — любой плагин, хранящий "текущий сценарий" в `self.attr`, тихо ломается (п. 9 плана 01) | 🔴 Высокий — плюс риск несовместимости C-расширений тестового стека (п. 2 плана 02) | 🟢 Минимальный — плагины продолжают работать как в обычном последовательном прогоне, каждый в своём процессе | 🟢 Минимальный — по тем же причинам, что у 03 (реальное исполнение сценария всегда монотонно внутри одного дочернего процесса) |
| Итоговый отчёт / единая точка выхода | — | — | 🟡 Отдельный мерж-скрипт вне vedro, свой формат вывода, нужно поддерживать отдельно от штатных репортеров | ✅ Единый `Report`, собранный в основном процессе штатным способом — нет отдельного "второго" формата отчёта |
| Реконструкция исключений/traceback | Полная (тот же процесс, живые объекты) | Требует явной сериализации (см. план 02, риск потери "живых" фреймов) | Текстовая сводка через `JsonReporter`/мерж-скрипт (тот же компромисс, что и у 03a) | Текстовая сводка (тип/сообщение/файл/строка), синтетический `ExcInfo` — задокументированное ограничение (раздел 4 плана 03a) |

Легенда: ✅ хорошо / 🟢 низкий риск или простота / 🟡 средне / 🔴 плохо, высокий риск или сложность.

## 3. Взвешенный итог

Если считать по количеству "🔴" (существенные минусы):
- **01 (asyncio)** — 2 красных (глубина патчей, риск для сторонних плагинов), но всё остальное умеренно или хорошо.
- **02 (sub-interpreters)** — 6 красных практически по всем ключевым критериям: версия Python, зрелость, сложность, риск, UX, сторонние плагины.
- **03 (внешний скрипт)** — 1 красный (overhead запуска), остальное зелёное/приемлемое, но есть системная слабость — "второй", несвязанный со штатным, формат итогового отчёта.
- **03a (плагин-оркестратор)** — 0 красных; есть один жёлтый пункт с более высокой значимостью, чем у 03 (использование деприкируемой точки `Registry.ScenarioRunner`), и чуть более высокая сложность реализации, но взамен — устранена системная слабость варианта 03 (отчёт становится штатным, а не отдельным).

## 4. Рекомендация

**Выбор: вариант 03a — плагин-оркестратор подпроцессов `vedro run` с реконструкцией
результатов в родном `Dispatcher`/`Report` основного процесса.**

Обоснование (относительно ближайшего конкурента — варианта 03):
- Даёт тот же **настоящий** параллелизм по CPU и ту же максимальную изоляцию
  состояния (ОС-процесс), что и вариант 03 — все проблемы глобального
  состояния из планов 01/02 (`os.chdir`, `StepRecorder`, `Deferrer._queue`,
  `OutputCapturer`) здесь так же отсутствуют "по построению".
- Устраняет системную слабость варианта 03 — итоговый отчёт больше не
  результат отдельного мерж-скрипта вне vedro, а штатный `Report`,
  собранный через реальные события `Dispatcher`: все существующие
  репортеры (Rich/Json/PyCharm) и сторонние плагины-репортеры продолжают
  работать без единой строчки адаптации под "параллельный формат".
- Даёт live-прогресс "бесплатно" (события ретранслируются в реальном
  времени по мере поступления NDJSON от воркеров), а не через грубую
  ретрансляцию сырого stdout с префиксами воркера.
- Единственная реальная цена по сравнению с 03 — использование точки
  `Registry.ScenarioRunner.register(...)`, которая помечена как
  "не для кастомных раннеров, будет удалена в v2" (то же самое ограничение,
  что и у варианта 01 — не новый риск, а уже принятый в экосистеме
  прецедент, т.к. этим же путём идёт встроенный `DryRunner`), и чуть более
  высокая сложность реализации (партиционирование без дублирования
  discovery, построчный парсинг NDJSON "на лету", реконструкция
  `ScenarioResult`/синтетического `ExcInfo`, passthrough CLI-аргументов).
- Наименьший риск сломать сторонние пользовательские плагины "исподтишка" —
  как и в варианте 03, реальное исполнение каждого сценария всегда
  монотонно внутри одного дочернего процесса.

Рекомендуемая последовательность:
1. Начать сразу с варианта 03a как основной цели — дополнительная сложность
   относительно "чистого" варианта 03 умеренная (не сопоставима по объёму
   с патчами планов 01/02), а выигрыш в виде единого штатного отчёта и
   live-прогресса существенно перевешивает эту разницу. Вариант 03
   (внешний скрипт) держать как fallback/самый быстрый MVP-путь, если
   ресурсов на плагин пока нет, либо как временное решение на время
   разработки 03a.
2. Параллельно (не блокируя п.1) начать вариант 01 как **дополнение**, а не
   замену — для случаев, где overhead запуска процессов не оправдан
   (маленькие сьюты, локальная разработка), после того как будут закрыты
   блокирующие патчи (п. 1, 3, 4, 8 из плана 01).
3. Вариант 02 (sub-interpreters) оставить в бэклоге как R&D — возвращаться к
   нему только если появятся конкретные CPU-bound кейсы, для которых ни 01,
   ни 03/03a не дают приемлемого решения, и только на проектах, готовых
   зафиксировать минимальную версию Python 3.13+.
