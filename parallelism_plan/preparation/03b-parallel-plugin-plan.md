# План реализации: плагин параллельного запуска (worker-id + группировка сценариев)

Документ развивает подход **03a** (`03a-plugin-based-subprocess-orchestrator.md`)
до технического задания. Ограничение задачи: **исходный код `vedro` править
нельзя** — только подключить плагин через `vedro.cfg.py`. Ниже перечислены все
точки публичного API vedro, которых достаточно для реализации, без патчей ядра.

Именование (имя пакета плагина, имя CLI-флага, префикс переменных окружения)
в документе намеренно оставлено абстрактным — задаётся на этапе внедрения.
Далее используются плейсхолдеры:
- `<parallel-plugin>` — разрабатываемый плагин параллельного запуска;
- `<env-plugin>` — **уже существующий** плагин проекта, который поднимает
  окружения/контейнеры;
- `--parallel=N` — CLI-флаг числа воркеров (реальное имя определяется при
  внедрении, например может предоставляться `<env-plugin>`, см. раздел 2);
- `PARALLEL_WORKER_ID` / `PARALLEL_WORKERS_TOTAL` — переменные окружения
  (реальный префикс определяется при внедрении).

## 1. Требования

1. CLI-параметр вида `--parallel=N` — число параллельных потоков (воркеров).
   `N <= 1` или отсутствие флага = обычный последовательный прогон, плагин
   полностью прозрачен.
2. Сторонний плагин (`<env-plugin>`, поднимающий контейнеры) должен уметь
   получать **идентификатор потока** (`worker_id`), чтобы разводить порты,
   имена контейнеров, БД и т.п. Способы доступа — оба:
   - переменная окружения процесса `PARALLEL_WORKER_ID` (+ `PARALLEL_WORKERS_TOTAL`);
   - Python API: `get_worker_id()` / `get_workers_total()`.
3. Сценарии объявляют требуемое окружение атрибутом класса:
   ```python
   class Scenario(vedro.Scenario):
       env = Envs.WITH_KAFKA
   ```
   Сценарии нужно **группировать по этому признаку** так, чтобы внутри одного
   воркера сценарии одной группы шли подряд — тогда `<env-plugin>` сможет
   переподнимать контейнеры только на границе смены группы, а не на каждом
   сценарии.
4. Никаких изменений в `vedro` — только внешний плагин.

## 2. Разделение ответственности: один плагин или два?

**Рекомендация: разделить на два независимых плагина.**

| Ответственность | Где реализуется |
|---|---|
| Партиционирование сценариев, запуск N процессов, сбор и склейка результатов, предоставление `worker_id` | `<parallel-plugin>` (новый) |
| Семантика `env`, подъём/переподнятие контейнеров, разведение портов по `worker_id` | `<env-plugin>` (существующий) |

Почему разделять, а не совмещать:
- `<parallel-plugin>` не должен знать ничего про `env`, `Envs`, контейнеры и
  докер — это делает его переиспользуемым в других проектах и независимо
  тестируемым;
- `<env-plugin>` не должен знать про подпроцессы, NDJSON и оркестрацию —
  он лишь читает `worker_id` и реагирует на смену группы;
- разные циклы изменений: логика окружений меняется часто (новые сервисы,
  новые env), логика параллелизма — редко;
- при удалении/отключении параллелизма `<env-plugin>` продолжает работать
  как раньше (worker_id = 0, одна группа за раз).

Тогда единственное, что нужно связать между ними, — **ключ группировки**.
`<parallel-plugin>` обязан знать, по какому признаку резать сценарии на
блоки, но **не должен** знать, что этот признак означает.

### 2.1 Контракт связи (три варианта, в порядке предпочтения)

1. **Callable в конфиге плагина (рекомендуется).**
   `<parallel-plugin>` объявляет в своём `PluginConfig` параметр вида
   `grouping_key: Callable[[VirtualScenario], Optional[str]]` со значением по
   умолчанию `None` (= не группировать). Проект в `vedro.cfg.py` подставляет
   туда функцию, которая читает `env` (её может экспортировать `<env-plugin>`).
   Плюсы: нулевая связанность между плагинами, обе стороны ничего не знают
   друг о друге, поведение полностью в руках проекта.
2. **Имя атрибута в конфиге.**
   Параметр `grouping_attr: str = "env"` — плагин сам читает атрибут с этим
   именем публичным способом (см. 3.4). Проще в настройке, но плагин
   параллелизма получает жёсткое допущение «группа — это строка/Enum в
   атрибуте класса».
3. **Через scenario meta.**
   `<env-plugin>` на `StartupEvent` проставляет каждому сценарию
   `scenario.set_meta("group", value, plugin=self)`, а `<parallel-plugin>`
   читает его. Минус: требует согласования порядка обработчиков (приоритетов
   подписки) и делает связь неявной.

Во всех трёх вариантах ядро vedro не патчится.

## 3. Перечень вызовов/точек расширения vedro, которые потребуются

Всё перечисленное — существующий публичный (или де-факто используемый
встроенными плагинами) API.

### 3.1 Каркас плагина

| Что нужно | API vedro | Комментарий |
|---|---|---|
| Объявить плагин и его конфиг | `vedro.core.Plugin`, `vedro.core.PluginConfig` | Стандартный каркас: `plugin = ...`, `description = ...` |
| Подписка на события | `Plugin.subscribe(dispatcher)` + `Dispatcher.listen(EventType, handler)` | Цепочка `.listen(...).listen(...)`, как в `SlicerPlugin` |
| Доступ к глобальному конфигу (для DI-регистраций) | `vedro.events.ConfigLoadedEvent` → `event.config` (тип `vedro.core.ConfigType`) | Обязательно: без него нет доступа к `Registry` |
| Добавить CLI-флаг | `vedro.events.ArgParseEvent` → `event.arg_parser.add_argument_group(...)` → `group.add_argument("--parallel", type=int, default=0, ...)` | Как в `SlicerPlugin.on_arg_parse` |
| Прочитать значение флага | `vedro.events.ArgParsedEvent` → `event.args.<dest>` | Валидация `N >= 1` здесь же |
| Подключение пользователем | В `vedro.cfg.py` внутри `class Plugins(vedro.Config.Plugins)` | Ничего в ядре менять не нужно |

### 3.2 Подмена раннера (ядро параллелизма)

| Что нужно | API vedro | Комментарий |
|---|---|---|
| Зарегистрировать собственный раннер | `event.config.Registry.ScenarioRunner.register(resolver=lambda: <Runner>(...), registrant=self)` | Выполняется в `on_arg_parsed`, только если `N > 1`. Ровно так же делает встроенный `DryRunnerPlugin` |
| Базовый интерфейс раннера | `vedro.core.ScenarioRunner` (`async def run(self, scheduler, **kwargs) -> Report`) | Раннер плагина наследуется от него |
| Получить `Dispatcher` для ретрансляции событий | `event.config.Registry.Dispatcher()` | Тот же (Frozen)Singleton, что и у всех плагинов основного процесса |
| Возврат результата | `vedro.core.Report` — `report.add_result(...)`, `report.add_summary(...)` | `RunCommand` берёт то, что вернул `runner.run(...)` |

⚠️ Единственный «серый» момент: `vedro/_config.py` помечает
`Registry.ScenarioRunner` как не предназначенный для кастомных раннеров
(будет удалён в v2), а `RunCommand` выдаёт `DeprecationWarning` для раннера,
не являющегося `MonotonicScenarioRunner`/`DryRunner`. В ветке 1.x это не
мешает (прецедент — сам `DryRunner`), но требует закрепления верхней границы
версии vedro в зависимостях плагина.

### 3.3 Доступ к сценариям и партиционирование

| Что нужно | API vedro | Комментарий |
|---|---|---|
| Список сценариев для распределения | `vedro.events.StartupEvent` → `event.scheduler`; `scheduler.discovered`, `scheduler.scheduled` | `StartupEvent` фаерится **до** создания раннера, поэтому в нём удобно зафиксировать финальный (уже отфильтрованный `Tagger`/`Skipper`/`Slicer`) состав прогона |
| Тот же список внутри раннера | Первый аргумент `run(self, scheduler, ...)` — `vedro.core.ScenarioScheduler` | Дублирует пункт выше; достаточно любого из двух |
| Идентификация сценария | `VirtualScenario.unique_id` (стабильная строка `rel_path::Name[#template_index]`), `VirtualScenario.unique_hash` | `unique_id` — ключ сопоставления результата воркера с объектом сценария в родителе |
| Указание сценария дочернему процессу | `VirtualScenario.rel_path`, `.path`, `.lineno`, `.name` | `vedro run` принимает пути файлов позиционно; точечный отбор — см. 5.2 |
| Исключение сценария из выполнения | `scheduler.ignore(scenario)` | Основной механизм отбора партии внутри воркера |
| Агрегация результатов | `scheduler.aggregate_results([...]) -> AggregatedResult` | Штатная агрегация, чтобы `--repeat`/`--reruns` считались как в монотонном раннере |

### 3.4 Чтение признака группировки у сценария

| Что нужно | API vedro | Комментарий |
|---|---|---|
| Прочитать атрибут класса сценария (`env = Envs.WITH_KAFKA`) | `VirtualScenario.get_meta("<attr>", plugin=self, default=None, fallback_key="<attr>")` | **Важно:** `fallback_key` заставляет vedro прочитать обычный атрибут класса. Полностью публичный путь — не нужно обращаться к приватному `scenario._orig_scenario` |
| Нормализация значения | Значение может быть `Enum` — берём `.value` (по аналогии с обработкой `Enum`-тегов в `TaggerPlugin._get_tags`) | Ключ группы — строка; сценарии без признака → группа по умолчанию |
| (опционально) Записать нормализованную группу обратно | `VirtualScenario.set_meta("group", value, plugin=self)` | Позволяет другим плагинам читать её тем же публичным способом |
| Альтернативный источник признака | `VirtualScenario.tags` | Не требуется при схеме с атрибутом, но можно поддержать вторым источником |

### 3.5 Ретрансляция событий в основной процесс

Чтобы штатные репортеры (Rich/Json/PyCharm) отработали без правок, раннер
плагина файрит в `Dispatcher` основного процесса те же события, что файрил бы
`MonotonicScenarioRunner`:

| Событие | Класс | Когда файрить |
|---|---|---|
| Старт сценария | `vedro.events.ScenarioRunEvent(scenario_result)` | При получении соответствующей записи из NDJSON воркера |
| Пропуск | `vedro.events.ScenarioSkippedEvent(scenario_result)` | — |
| Шаги | `vedro.events.StepRunEvent` / `StepPassedEvent` / `StepFailedEvent` | По записям шагов |
| Исключение | `vedro.events.ExceptionRaisedEvent(exc_info)` | Перед `StepFailedEvent` (синтетический `ExcInfo`, см. 5.3) |
| Итог сценария | `vedro.events.ScenarioPassedEvent` / `ScenarioFailedEvent` | — |
| Финальный результат | `vedro.events.ScenarioReportedEvent(aggregated_result)` | После агрегации |

Объекты результатов создаются публичными конструкторами/сеттерами:
`vedro.core.ScenarioResult(scenario)` + `set_started_at` / `set_ended_at` /
`mark_passed` / `mark_failed` / `mark_skipped` / `add_step_result` / `set_scope` /
`add_extra_details` / `set_captured_output`; `vedro.core.StepResult(virtual_step)`
с аналогичным набором; `vedro.core.AggregatedResult.from_existing(main, results)`.
`VirtualScenario` **не пересоздаётся** — берётся существующий объект из
`scheduler.discovered` по `unique_id`.

### 3.6 Машинный формат обмена родитель↔воркер

| Что нужно | API vedro | Комментарий |
|---|---|---|
| Поток структурированных событий из воркера | Встроенный `JsonReporter` (`--reporter json`), NDJSON в stdout | Схема — `vedro/plugins/director/json/_event_types.py` (`ScenarioDict`, `StepDict`, `ExcInfoDict`, `ReportDict`) |
| Выбор репортера в дочернем процессе | CLI-флаг `--reporter json`, пробрасываемый оркестратором | Родитель остаётся со своим репортером (Rich и т.д.) |

Рекомендация: обернуть чтение NDJSON в отдельный слой-адаптер, чтобы при
изменении схемы `JsonReporter` менять только его (схема не является
стабильным публичным контрактом vedro).

### 3.7 Прочее

| Что нужно | API vedro | Комментарий |
|---|---|---|
| Сводка в отчёте (воркеры, распределение групп) | `CleanupEvent` → `event.report.add_summary("...")` | Как в `RerunnerPlugin.on_cleanup` |
| Преамбула (план распределения) | `event.report.add_preamble(...)` на `StartupEvent` | Опционально |
| Изоляция temp-директорий воркеров | CLI `--tmp-dir` (плагин `TempKeeper`) — свой путь каждому воркеру | Иначе гонки при `shutil.rmtree` общей `.vedro/tmp/` |
| Прекращение при `--fail-fast` | Родитель считает падения по `ScenarioReportedEvent` и рассылает `SIGTERM` дочерним | Внутри воркеров штатный `InterrupterPlugin` работает как обычно |
| Защита от рекурсии | Если `PARALLEL_WORKER_ID` уже в окружении — дочерний процесс не разворачивает воркеров повторно | Проверяется в `on_arg_parsed` до регистрации раннера |

## 4. Идентификатор потока (worker id)

### 4.1 Канал передачи

Родительский оркестратор при запуске i-го дочернего процесса выставляет ему
в окружении:
- `PARALLEL_WORKER_ID` — индекс воркера (рекомендуется 0-based, как
  `--slicer-index` в ядре; в человекочитаемом выводе можно показывать 1-based);
- `PARALLEL_WORKERS_TOTAL` — общее число воркеров;
- (опционально) `PARALLEL_WORKER_GROUPS` — список групп, назначенных этому
  воркеру, чтобы `<env-plugin>` мог заранее подготовить только нужные
  окружения, а не все.

### 4.2 Python API для `<env-plugin>`

`<parallel-plugin>` экспортирует функции-геттеры, читающие те же переменные:
- `get_worker_id() -> int` — `0`, если запуск последовательный (не под
  оркестратором); это делает API безопасным для обычного однопоточного
  прогона без ветвлений в коде потребителя;
- `get_workers_total() -> int` — `1` в последовательном режиме;
- `is_parallel_worker() -> bool` — признак работы под оркестратором;
- `get_worker_groups() -> list[str] | None` — назначенные воркеру группы.

Геттеры читают **окружение процесса**, а не состояние объекта плагина,
поэтому доступны из любого места (в т.ч. из кода тестов и из плагинов без
ссылки на объект `<parallel-plugin>`) и работают уже на самой ранней стадии
старта дочернего процесса — до `StartupEvent` и до первого сценария.

> Следствие для разделения ответственности (раздел 2): `<env-plugin>` зависит
> от `<parallel-plugin>` **только** через эти геттеры, а при их отсутствии
> может использовать прямое чтение переменных окружения с теми же дефолтами —
> то есть жёсткая зависимость пакетов необязательна.

### 4.3 Отслеживание смены группы внутри воркера

Чтобы `<env-plugin>` переподнимал контейнеры ровно на границе смены группы,
он подписывается на штатный `ScenarioRunEvent` и читает признак текущего
сценария тем же публичным способом:
`event.scenario_result.scenario.get_meta("<attr>", plugin=self, default=None, fallback_key="<attr>")`,
сравнивая с запомненным предыдущим значением. Вводить события собственного
типа не требуется — достаточно `ScenarioRunEvent` и сравнения.

Порядок сценариев внутри воркера гарантирован тем, что дочерний процесс
исполняет свою партию **строго последовательно** штатным
`MonotonicScenarioRunner`, а порядок партии задан родителем (раздел 5).

## 5. Группировка и распределение по воркерам

### 5.1 Алгоритм

1. Родитель получает список сценариев (`scheduler.discovered`) после того, как
   отработали все фильтрующие плагины (`Tagger`, `Skipper`, `Slicer`) — то есть
   на `StartupEvent` или в начале `run()`.
2. Для каждого сценария вычисляется ключ группы — через контракт из 2.1
   (callable из конфига либо чтение атрибута), с нормализацией `Enum → .value`.
3. Сценарии группируются в блоки; блоки сортируются по убыванию размера
   (эвристика LPT — longest processing time first — по количеству сценариев,
   а при наличии истории таймингов — по суммарному времени).
4. Блоки раскладываются по N воркерам жадно: очередной блок целиком отдаётся
   наименее загруженному воркеру. Целостность блока — приоритет: разбивать
   блок допустимо **только** если он один больше, чем `общий объём / N`
   (иначе воркеры простаивают); части всё равно остаются смежными внутри
   своего воркера.
5. Внутри воркера порядок партии = блоки подряд, порядок сценариев внутри
   блока сохраняется исходный (важно для воспроизводимости).
6. Все копии одного `unique_id` (повторы при `--repeat`/`--reruns`)
   обязательно попадают в один воркер — иначе сломается штатная агрегация.

Компромисс, который нужно зафиксировать в документации плагина: при малом
числе групп и большом N часть воркеров может простаивать (нельзя одновременно
идеально сбалансировать нагрузку и минимизировать число переключений группы).
Управляется политикой: `--parallel-balance=group-affinity|even`
(по умолчанию `group-affinity` — реже переключать окружения).

### 5.2 Как передать партию дочернему процессу

Простой путь — передать список **файлов** позиционными аргументами
`vedro run <path1> <path2> ...`. Ограничение: если в одном файле несколько
сценариев/шаблонов, а партиционирование развело их по разным воркерам,
пофайловой гранулярности не хватит. Варианты (в порядке предпочтения):

1. **Точечный отбор внутри воркера (рекомендуется).** Передать воркеру список
   `unique_id` (через файл или переменную окружения) и в дочернем процессе
   включить вспомогательную часть того же плагина, которая на `StartupEvent`
   вызывает `scheduler.ignore(scenario)` для всех сценариев не своей партии —
   ровно тот механизм, которым пользуется встроенный `SlicerPlugin`. Точность
   до сценария, правок ядра не требует.
2. **Файловая гранулярность как грубый фильтр.** Ускоряет discovery в воркере;
   если сценарии одного файла попали в разные партии — слить их в одну.
3. Комбинация 2 + 1: файлы как грубый фильтр, `ignore()` по `unique_id` —
   как точный.

### 5.3 Ограничение по исключениям

Как и в 03a: живой traceback через границу процесса не передаётся. Из NDJSON
доступны `type` / `message` / `file` / `lineno` (+ текстовое представление), на
их основе создаётся синтетический `ExcInfo`. Репортеры, печатающие traceback
как текст, работают штатно; программный анализ фреймов невозможен.
Зафиксировать в README плагина.

## 6. Состав `<parallel-plugin>` (модули)

1. **Config** (`PluginConfig`) — `--parallel=N`,
   `--parallel-balance=group-affinity|even`, контракт ключа группировки
   (см. 2.1), таймауты дочерних процессов.
2. **Plugin** (`Plugin`) — подписки (`ConfigLoadedEvent`, `ArgParseEvent`,
   `ArgParsedEvent`, `StartupEvent`, `CleanupEvent`), регистрация раннера,
   защита от рекурсии, сводка в отчёте.
3. **Runner** (`ScenarioRunner`) — партиционирование, запуск дочерних процессов
   (`asyncio.create_subprocess_exec` с `env=...`), построчное чтение NDJSON,
   ретрансляция событий, сборка `Report`.
4. **Grouper** — вычисление и нормализация ключа группы, группировка,
   балансировка (не знает про `env`/контейнеры — только про абстрактный ключ).
5. **ResultReconstructor** — NDJSON → `ScenarioResult` / `StepResult` /
   `AggregatedResult` / синтетический `ExcInfo`, сопоставление по `unique_id`.
6. **WorkerFilter** (активен только в дочернем процессе) — на `StartupEvent`
   вызывает `scheduler.ignore(...)` для сценариев не своей партии.
7. **worker_api** — публичные `get_worker_id()`, `get_workers_total()`,
   `is_parallel_worker()`, `get_worker_groups()`.

Вне периметра `<parallel-plugin>` (реализуется в `<env-plugin>`):
подъём/остановка контейнеров, разведение портов и имён ресурсов по
`worker_id`, реакция на смену группы через `ScenarioRunEvent`.

## 7. Итог: что НЕ требуется от vedro

Для реализации не нужен ни один патч ядра:
- параллелизм — за счёт дочерних процессов, а не конкурентности внутри
  процесса, поэтому проблемы `os.chdir`, глобального `OutputCapturer`,
  синглтона `StepRecorder` и общей очереди `Deferrer` (см. план 01)
  **не возникают вовсе**;
- чтение признака группировки — публичный
  `VirtualScenario.get_meta(..., fallback_key=...)`;
- отбор партии — публичный `scheduler.ignore(...)`;
- подмена раннера — существующий `Registry.ScenarioRunner.register(...)`
  (единственная зависимость от помеченного deprecated-к-v2 API);
- отчётность — штатные события `Dispatcher` и штатный `Report`.
