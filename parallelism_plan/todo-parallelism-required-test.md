## Открытые кейсы, тесты ещё не написаны

### 1. Баг переиспользования при `parallelism_limit > 1` (B1)

`calc_broken_services` сравнивает имена сервисов шаблона (`s1`) с реальными
именами сервисов из `docker compose ps` (`s1-<env_id>`) — они никогда не
совпадают при ненулевом суффиксе env_id, поэтому `_find_reusable_env` всегда
считает окружение «не готовым» и штампует новый namespace на каждый `up()`,
даже если такой же шаблон уже поднят и здоров.

Зафиксировано тестом `102_*` (красный). Нужно: починить сопоставление имён
(учитывать `env_id`-маппинг при сравнении) и сделать тест зелёным.

### 2. Ложный `AFTER_UPDATED_ENV_UP` для несвязанного нового env

`_previous_release_id` хранится на уровне клиента (`SystemUberCompose`)
глобально, а не per-шаблон (`uber_compose.py:67,161,241,290,292`). Подозрение:
если один и тот же клиент (в проде — `TheUberCompose`, синглтон, которым
реально пользуется vedro-плагин) поднимает **два разных, не связанных**
env-шаблона подряд, второй `up()` может ошибочно получить
`is_env_update=True` и выстрелить хук `AFTER_UPDATED_ENV_UP`, хотя это не
апдейт существующего окружения, а подъём независимого нового.

Нужно: тест с `TheUberCompose` (или любым клиентом, переиспользуемым между
вызовами) — поднять env A, затем совершенно другой env B → проверить, что для
B срабатывает только `AFTER_UP`, а `AFTER_UPDATED_ENV_UP` не вызывается.
Разместить рядом с `tests/scenarios/700_hooks/`.

### 3. SINGLETON не работает вместе с `parallelism_limit > 1` (B4)

`get_service_map` (`core/utils/compose_instance_cfg.py`) переименовывает
*все* сервисы кроме `ServiceMode.OFF` — `ServiceMode.SINGLETON` не исключается.
Плюс вся логика защиты singleton-сервисов от рестарта
(`_compute_singleton_protected_services`) вызывается только внутри ветки
`if parallelism_limit == 1` в `_start_new_environment`. То есть сейчас
`singleton()`-маркер и `parallelism_limit > 1` — полностью не
взаимодействующие друг с другом фичи: при параллелизме singleton-сервис так
же получает суффикс `-<env_id>` и дублируется на каждый namespace, никакой
защиты от рестарта нет.

Нужно: тест с singleton-сервисом в шаблоне + `parallelism_limit=2`,
зафиксировать текущее (видимо неверное) поведение как красный тест, затем
решить семантику (это прямой блокер для §2 design-дока — гибридная изоляция
инфраструктуры).

### 4. `wait_all_services_up` проверяет весь compose-проект, а не свой namespace (B3)

`core/utils/state_waiting.py` / вызов из `core/docker_compose.py:run_services_pack`
смотрит на состояние всего compose-проекта целиком. При нескольких
одновременно поднимаемых namespace'ах (`parallelism_limit > 1`) ожидание
здоровья одного env потенциально зависит от состояния другого, ещё не
готового/уже сломанного namespace.

Нужно: тест — поднять env A с сервисом, который долго становится healthy (или
сразу unhealthy), затем параллельно/следом поднять env B с обычным healthy
сервисом → проверить, что `up(B)` не ждёт/не падает из-за состояния A.

### 5. Ветка плагина `parallel_env_limit < len(needed_configs)` не протестирована

В `vedro_plugin/plugin.py:handle_prepare_scenarios` пре-ап всех нужных env
сразу происходит только если `parallel_env_limit >= len(needed_configs)`.
Если шаблонов больше, чем лимит, пре-ап не происходит вообще, и среды
поднимаются по одной в `handle_pre_run_scenario`. Существующий тест
`800_vedro_plugin/110_handle_scenarios_with_in_range_of_parallelism_limit_env.py`
покрывает только случай `limit >= needed`. Нет теста на случай
`limit < needed`.

Нужно: тест с `parallel_env_limit=1` (или 2) и 3 разными env-шаблонами в
сценариях — проверить, что `StartupEvent` не поднимает их все разом, а каждый
поднимается непосредственно перед своим сценарием.

### 6. `exec()` в многонамespace-окружении

`SystemUberCompose.exec()` (`uber_compose.py:300`) не проверялся в ситуации,
когда несколько инстансов одного и того же шаблона/сервиса подняты
одновременно (`parallelism_limit > 1`) — нет уверенности, что команда
выполняется именно в контейнере нужного (последнего поднятого/явно
указанного) namespace, а не в произвольном/первом попавшемся.

Нужно: тест — поднять env A и env B (оба с сервисом `s1`, `limit=2`),
вызвать `exec()` для конкретного `env_id`/инстанса → убедиться, что команда
выполнилась в контейнере нужного namespace, а не соседнего.
