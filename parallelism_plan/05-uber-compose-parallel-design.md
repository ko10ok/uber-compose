# Параллельный прогон в uber-compose: неймспейсы + плагин-оркестратор

Документ отвечает на вопрос «делать параллелизм отдельным плагином или встраивать
в текущий `VedroUberComposePlugin`» и фиксирует целевую архитектуру для дальнейшей
реализации. Опирается на:

- `preparation/03a-plugin-based-subprocess-orchestrator.md` — оркестрация подпроцессов плагином;
- `preparation/03b-parallel-plugin-plan.md` — ТЗ на `<parallel-plugin>` (worker-id + группировка);
- `preparation/04-comparison-and-recommendation.md` — выбор варианта 03a как основного.

Этот документ — слой «как это ложится на uber-compose»: неймспейсы окружений,
общая инфраструктура (kafka/postgres), разделение ответственности, ограничения
текущего кода. **Реализации в нём нет — только проект.**

Принятые вводные (согласованы):

1. Упаковка: **два независимых vedro-плагина в одной дистрибуции `uber-compose`**.
2. Изоляция инфраструктуры: **гибрид** — `SINGLETON`-сервисы (kafka, postgres)
   один экземпляр на все воркеры + логическая изоляция внутри (БД/топик с
   суффиксом воркера); остальные сервисы — свой контейнер на неймспейс.

---

## 1. Что в uber-compose уже готово для параллелизма

Механика неймспейсов фактически уже есть, она используется для «нескольких env
в одном прогоне», и её же можно переиспользовать для «нескольких воркеров»:

| Механизм | Где | Что даёт |
|---|---|---|
| `env_id` и переименование сервисов `f'{service}-{env_id}'` | `core/utils/compose_instance_cfg.py: make_env_service_name/get_service_map` | Физический неймспейс контейнеров внутри одного compose-проекта |
| Подстановка `[[service]]` → реальное имя в env сервисов | `compose_instance_cfg.py: sub_env_id/prepare_services_env` | Сервисы неймспейса видят друг друга по правильным именам |
| Подстановка `[[test_run_id]]` | `core/utils/compose_files.py: patch_envs`, `vedro_plugin/helpers/test_env_vars_setter.py` | Готовый шаблонный механизм для уникализации ресурсов — база для `[[worker_id]]` |
| Лейблы `ENV_ID / ENV_CONFIG_TEMPLATE / COMPOSE_FILES / SERVICE_NAME` | `helpers/labels.py`, `core/utils/compose_files.py: make_env_compose_instance_files` | Поиск и переиспользование уже поднятых окружений |
| Отдельная tmp-директория инстанса `/tmp/uc-envs/<env_id>` | `compose_files.py: make_env_compose_instance_files` | Патченные compose-файлы не конфликтуют между неймспейсами |
| `ComposeConfig.parallel_env_limit` | `core/sequence_run_types.py` | Уже существующий «переключатель» между default-режимом и неймспейсами |
| `EnvTagsOrderer` | `vedro_plugin/helpers/scenario_ordering.py` | Сценарии уже группируются по env — основа для партиционирования |
| Один `COMPOSE_PROJECT_NAME` на всё | `core/constants.py` | Все неймспейсы в одном проекте/сети — общая инфраструктура достижима без внешних сетей |
| `ServiceMode.SINGLETON` | `env_description/env_types.py`, `env_tools.py: singleton()` | Объявлен API общей единицы… но не реализован (см. §2) |

Вывод: **новую модель изоляции изобретать не нужно.** Параллелизм = «выделить
каждому воркеру свой `env_id` на каждый нужный ему env-шаблон» + запуск сценариев
в N процессах.

## 2. Блокеры в текущем коде (must-fix перед параллелизмом)

Найдено при разборе кода; каждый пункт — отдельная задача реализации.

| # | Блокер | Где | Последствие в параллели |
|---|---|---|---|
| B1 | Поиск переиспользуемого окружения матчится только по `(ENV_CONFIG_TEMPLATE, COMPOSE_FILES)` и берёт `get_any()` | `core/system_docker_compose.py: get_state_for`, `uber_compose.py: _find_reusable_env` | Два воркера с одинаковым env получат **один и тот же** неймспейс → взаимное влияние тестов |
| B2 | При `parallelism_limit == 1` используется `DEFAULT_ENV_ID` и делается `down` всех «чужих» сервисов | `uber_compose.py: _start_new_environment` | Воркер сносит окружения других воркеров |
| B3 | `wait_all_services_up` проверяет **весь** compose-проект, а не сервисы своего неймспейса | `core/utils/state_waiting.py`, вызов из `core/docker_compose.py: run_services_pack` | Подъём одного неймспейса ждёт/падает из-за соседнего, который ещё стартует |
| B4 | `ServiceMode.SINGLETON` не учитывается: `get_service_map` переименовывает всё, кроме `OFF` | `compose_instance_cfg.py: get_service_map` | Нельзя объявить kafka/postgres общими — они дублируются на каждый неймспейс |
| B5 | `setup_env_for_tests` пишет переменные в `os.environ` процесса | `vedro_plugin/helpers/test_env_vars_setter.py` | Внутрипроцессный параллелизм (asyncio/threads) невозможен в принципе → подтверждает выбор process-per-worker (03a) |
| B6 | `TheUberCompose` — синглтон процесса | `uber_compose.py`, `helpers/singleton.py` | То же: одна «активная» точка на процесс, безопасно только при модели процессов |
| B7 | Гонки при одновременном `docker compose up` в одном проекте (`--pull missing`, общая сеть, `dc_state` во время старта) | `core/docker_compose_shell/interface.py` | Флапы при «каждый воркер поднимает сам» → аргумент за пре-ап в родителе (§5) |
| B8 | Миграции (`x-migration`) выполняются на каждый инстанс окружения | `core/docker_compose.py: run_migration` | Для общих SINGLETON-сервисов миграции должны выполняться **один раз** |
| B9 | `up()` при подъёме нескольких env выполняется последовательно в `handle_prepare_scenarios` | `vedro_plugin/plugin.py` | Пре-ап N×M неймспейсов будет линейно долгим; нужен ограниченный конкурентный подъём |

## 3. Отдельный плагин или встраивание — решение

**Решение: два независимых плагина в одной дистрибуции `uber-compose`.**

```
uber_compose/
  vedro_plugin/            # существующий env-плагин (VedroUberCompose)
  parallel_plugin/         # новый: VedroUberComposeParallel (generic-оркестратор)
    plugin.py              # PluginConfig + Plugin, регистрация раннера
    runner.py              # ScenarioRunner: партиционирование, subprocess, NDJSON
    grouper.py             # ключ группы → блоки → раскладка по воркерам
    reconstructor.py       # NDJSON → ScenarioResult/StepResult/AggregatedResult
    worker_filter.py       # в дочернем процессе: scheduler.ignore(не своя партия)
    worker_api.py          # get_worker_id/get_workers_total/is_parallel_worker
```

Почему так, а не «всё в `VedroUberComposePlugin`»:

- оркестратор ничего не знает про docker/env — его можно тестировать и
  переиспользовать отдельно (в т.ч. вынести в свой пакет позже, §3.1);
- env-плагин ничего не знает про подпроцессы и NDJSON — он лишь читает
  `worker_id` и решает, какой неймспейс использовать;
- разные циклы изменений: env-логика меняется часто, параллелизм — редко;
- при отключённом параллелизме env-плагин работает ровно как сейчас
  (`worker_id = 0`, один неймспейс), т.е. регрессий по умолчанию нет.

Почему в одной дистрибуции, а не отдельным пакетом сразу:

- пользователю не нужно ставить и версионировать второй пакет ради `--uc-parallel`;
- e2e-набор `tests/` уже умеет проверять оба слоя в одном прогоне;
- граница между плагинами держится дисциплиной импортов (см. §3.1), поэтому
  вынос в отдельный пакет остаётся дешёвым, если понадобится.

### 3.1 Контракт между плагинами (обязателен к соблюдению)

Направление зависимости — **только** `vedro_plugin → parallel_plugin.worker_api`,
и то опционально (с фолбэком на чтение переменных окружения). Обратной
зависимости (`parallel_plugin → uber_compose.core/env_description`) быть не должно.

1. **Переменные окружения** (родитель → воркер):
   `UC_WORKER_ID`, `UC_WORKERS_TOTAL`, `UC_WORKER_GROUPS`, `UC_NAMESPACE_MAP`
   (см. §4.4). Читаются на самом раннем этапе, до `StartupEvent`.
2. **Ключ группировки** — `grouping_key: Callable[[VirtualScenario], str | None]`
   в конфиге параллельного плагина. В `vedro.cfg.py` проект подставляет функцию
   из uber-compose (`uber_compose.vedro_plugin.grouping.env_group_key`), которая
   считает хеш env-шаблона сценария (`base64_pickled(extract_scenario_config(...))`).
   Это вариант №1 из `03b §2.1` — нулевая связанность.
3. **Python API** для env-плагина: `get_worker_id()`, `get_workers_total()`,
   `is_parallel_worker()`, `get_worker_groups()` — с безопасными дефолтами
   (`0`, `1`, `False`, `None`) в последовательном режиме.

### 3.2 Отвергнутые варианты (кратко)

| Вариант | Почему не |
|---|---|
| Всё в текущем плагине (один класс, флаг `--uc-parallel`) | Смешивает две несвязанные ответственности, оркестратор становится непереиспользуемым, растёт риск регрессий в стабильной env-логике |
| Отдельный PyPI-пакет сразу | Лишняя версионная связка и синхронизация релизов на этапе, когда контракт ещё не устоялся |
| Внешний shell/py-скрипт над `vedro run` (план 03 «как есть») | Отдельный формат отчёта вне vedro; оставляем только как аварийный MVP |
| Внутрипроцессный asyncio-параллелизм (план 01) | Блокируется B5/B6 (`os.environ`, синглтон клиента) — потребовал бы переписать модель конфигурации env |

## 4. Модель неймспейсов

### 4.1 Определение

```
namespace = (env_template, worker_slot)  →  env_id
```

- `env_template` — существующий `Environment` сценария (то, по чему уже
  группирует `EnvTagsOrderer`);
- `worker_slot` — индекс воркера `0..N-1`;
- `env_id` — то, что уже подставляется в имена сервисов и лейблы.

Все неймспейсы живут **в одном compose-проекте и одной сети** — это и есть
«одна инфраструктура», в рамках которой шарятся SINGLETON-сервисы.

### 4.2 Именование `env_id` — варианты

| Вариант | Формат | Плюсы | Минусы |
|---|---|---|---|
| N1. Случайный (как сейчас) | `uuid4()[:4]` | Ничего не менять | Между прогонами не переиспользуется; локально каждый ре-ран поднимает новое |
| N2. Детерминированный по слоту и шаблону (**рекомендуется**) | `w{slot}-{hash4(template)}`, префикс `w{slot}-` **только при `--parallel>1`** (см. §10.1) | Стабильные имена → переиспользование окружений между прогонами, читаемые логи/контейнеры, простое ручное `docker ps` | Нужна аккуратность с длиной имён контейнеров и коллизиями хешей |
| N3. Только по слоту | `w{slot}` | Максимально коротко | Один слот не может держать несколько env-шаблонов одновременно → лишние ре-апы при смене группы |

Рекомендация: **N2**, с сохранением N1 как фолбэка, если хеш недоступен.
Ограничение длины имени сервиса проверять на этапе генерации (docker имя
контейнера = `project-service-1`).

### 4.3 Новые лейблы

К `helpers/labels.py` добавить:

- `WORKER_SLOT = 'com.maxwelld.worker_slot'` — индекс воркера (или `shared`);
- `NAMESPACE = 'com.maxwelld.namespace'` — человекочитаемый ключ неймспейса;
- `RUN_ID = 'com.maxwelld.run_id'` — id прогона (для массовой уборки).

Матчинг переиспользуемого окружения (B1) становится:
`(ENV_CONFIG_TEMPLATE, COMPOSE_FILES, WORKER_SLOT)`.

### 4.4 Передача плана воркеру

Родитель считает план заранее и передаёт воркеру готовую карту:

```
UC_WORKER_ID=2
UC_WORKERS_TOTAL=4
UC_WORKER_GROUPS=<hash_a>,<hash_b>
UC_NAMESPACE_MAP={"<hash_a>": "w2-a1b2", "<hash_b>": "w2-c3d4"}
```

Воркер тогда не «ищет любое подходящее окружение», а **адресно** берёт свой
`env_id` — это устраняет B1 полностью, даже без изменения логики поиска
(поиск остаётся как страховка/валидация).

## 5. Кто поднимает окружения

**Короткий ответ: uber-compose поднимает сразу все окружения в родительском
процессе — до того, как плагин параллелизма запустит воркеры. Внутри потоков
(воркеров) uber-compose ничего не поднимает, а только «прикрепляется» (attach) к
уже готовому неймспейсу и выставляет переменные окружения для тестов.**

### 5.0 Точный протокол (рекомендуемый вариант П1)

Родительский процесс:

1. `ConfigLoadedEvent` / `ArgParsedEvent` — параллельный плагин видит `--parallel=N`,
   регистрирует свой `ScenarioRunner`; env-плагин запоминает выбранный `ComposeConfig`.
2. `StartupEvent`, **сначала параллельный плагин**: по `scheduler` считает план —
   группы (по `grouping_key` = хеш env-шаблона), раскладку блоков по воркерам и
   карту `namespace_map: {worker_slot: {group_hash: env_id}}`. План публикуется как
   структура, доступная env-плагину (см. 5.0.1).
3. `StartupEvent`, **затем env-плагин** (`handle_prepare_scenarios`): берёт план и
   поднимает:
   - сначала общие `SINGLETON`-сервисы (один раз, вместе с их миграциями);
   - затем **все** неймспейсы плана — конкурентно, с семафором `up_concurrency`.
   Если плана нет (параллелизм выключен) — работает ровно как сегодня.
4. `runner.run(...)`: параллельный плагин порождает N процессов `vedro run ...` с
   `UC_WORKER_ID`, `UC_WORKERS_TOTAL`, `UC_WORKER_GROUPS`, `UC_NAMESPACE_MAP`.

Дочерний процесс (воркер):

5. env-плагин видит `UC_WORKER_ID` → включает режим **attach-only**:
   - `handle_prepare_scenarios` **не поднимает ничего** (нет ре-апа, нет `down`);
   - `handle_pre_run_scenario` резолвит `env_id` своего неймспейса по
     `UC_NAMESPACE_MAP[group_hash]`, читает `ENV_CONFIG` из лейблов уже поднятых
     контейнеров и вызывает `setup_env_for_tests(...)`;
   - если неймспейса нет/он сломан — поведение по политике
     `missing_namespace=fail|lazy-up` (по умолчанию `fail`: значит родитель
     ошибся в плане, а не воркер должен это чинить).

Итог: `docker compose up` вызывается **только в родителе**. Это снимает гонки
(B7), дублирование миграций SINGLETON (B8) и делает поведение воспроизводимым.

#### 5.0.1 Как план попадает из параллельного плагина в env-плагин

Не нарушая правило «плагины не знают друг о друге» (§3.1):

| Вариант | Механика | Оценка |
|---|---|---|
| П1-a. Публикация плана в `worker_api` (**рекомендуется**) | Параллельный плагин кладёт план в модульное состояние `parallel_plugin.worker_api.set_execution_plan(...)`; env-плагин вызывает `get_execution_plan()` и при `None` работает по-старому | Явный однонаправленный контракт, тот же модуль, что и геттеры `worker_id` |
| П1-b. Файл плана | План пишется в `<tmp>/uc-plan-<run_id>.json`, путь — в `UC_PLAN_FILE` | Не требует общей памяти, удобно для отладки; лишний файловый цикл |
| П1-c. Через `scenario.set_meta(...)` | Параллельный плагин помечает сценарии слотом, env-плагин агрегирует | Неявно, требует согласования приоритетов подписки |

В любом варианте нужен **гарантированный порядок обработчиков `StartupEvent`**:
параллельный плагин раньше env-плагина. Обеспечивается порядком объявления в
`vedro.cfg.py` + защитой в коде (env-плагин: если `--parallel>1`, но плана нет —
явная ошибка с подсказкой про порядок плагинов, а не молчаливый последовательный ап).

### 5.1 Сравнение вариантов «кто апает»

| Вариант | Схема | Плюсы | Минусы |
|---|---|---|---|
| П1. Пре-ап в родителе (**рекомендуется**) | Родитель: планирование → подъём SINGLETON → подъём всех неймспейсов (ограниченная конкурентность, семафор) → запуск воркеров, которые только читают env-переменные | Нет гонок docker (B7), миграции SINGLETON один раз (B8), понятный «долгий старт → быстрый прогон», воркеры стартуют уже на готовом | Пиковое потребление ресурсов сразу; при `N×M` неймспейсах стартап дольше, чем «первый тест пошёл» |
| П2. Каждый воркер сам | Воркер вызывает `up()` для своего неймспейса по ходу | Ленивость: поднимается только реально нужное | Гонки docker compose, дублирующиеся миграции SINGLETON, нужна межпроцессная файловая блокировка |
| П3. Гибрид | Родитель поднимает SINGLETON + по одному неймспейсу на воркер (первую группу), остальные — лениво в воркере под файловой блокировкой | Баланс скорости старта и ресурсов | Самая сложная логика; блокировка всё равно нужна |

Рекомендация: **П1** как целевая, **П3** — как последующая оптимизация под флагом.
В обоих случаях подъём SINGLETON-сервисов и их миграций — **только в родителе**.

Ограничение конкурентности пре-апа — отдельный параметр (`up_concurrency`),
иначе локальная машина ляжет на N×M одновременных `docker compose up`.

## 6. SINGLETON-сервисы (kafka, postgres) — общая инфраструктура

### 6.1 Физический уровень

- `get_service_map` (B4) не переименовывает сервисы с `mode=SINGLETON` —
  они получают базовое имя и лейблы `WORKER_SLOT=shared`, `ENV_ID=<shared_env_id>`.
- Поднимаются один раз родителем, до неймспейсов; входят в `depends_on`
  неймспейсных сервисов через `services_map` (маппинг singleton → сам себя).
- Подстановка `[[postgres]]`/`[[kafka]]` в env неймспейсных сервисов даёт
  общее имя — сетевая связность «из коробки», отдельные сети не нужны.
- Force restart (`--uc-fr`) по умолчанию **не** трогает SINGLETON (иначе один
  воркер уронит инфраструктуру всех); отдельный флаг `--uc-fr-all`.
- Health-ожидание своего неймспейса (B3) фильтруется по
  `ENV_ID ∈ {my_env_id, shared_env_id}`.

### 6.2 Логический уровень (изоляция внутри общего сервиса)

Расширить механизм подстановок (`patch_envs` + `setup_env_for_tests`) новыми
плейсхолдерами, наравне с существующим `[[test_run_id]]`:

- `[[worker_id]]` — индекс воркера;
- `[[namespace]]` — ключ неймспейса (`w2-a1b2`);
- `[[env_id]]` — id неймспейса.

Типовое применение:

```
POSTGRES_DB=app_[[worker_id]]
KAFKA_TOPIC_PREFIX=w[[worker_id]]_
REDIS_DB_INDEX=[[worker_id]]
```

Варианты создания per-worker ресурсов в общем сервисе:

| Вариант | Как | Комментарий |
|---|---|---|
| S1. Миграция-хук на общем сервисе (**рекомендуется**) | `x-migration: before_all` на SINGLETON создаёт БД/схемы/топики для всех слотов | Один раз в родителе, детерминированно, видно в compose-файле |
| S2. Ответственность неймспейсного сервиса | Приложение само создаёт свою БД/топик при старте | Проще для uber-compose, но перекладывает контракт на приложение |
| S3. Ничего не создавать | Тесты сами разводят данные (префиксы ключей) | Годится для kafka с auto-create topics, не годится для БД |

Документировать как явное ограничение: **при S3 изоляция «честная» только на
уровне соглашений тестов** — uber-compose её не гарантирует.

## 7. Планирование и распределение сценариев

Работает поверх `03b §5`, с уточнениями под uber-compose:

1. Ключ группы = хеш env-шаблона сценария (`base64_pickled`), т.е. ровно то, по
   чему уже сортирует `EnvTagsOrderer`.
2. Блоки одной группы идут внутри воркера подряд.
3. Раскладка блоков по воркерам — жадно (LPT по числу сценариев; по времени,
   если появится история таймингов).
4. Политика `--uc-parallel-balance`:
   - `group-affinity` (по умолчанию) — минимум разных групп на воркер →
     меньше неймспейсов и меньше ресурсов;
   - `even` — равномерная загрузка, ценой большего числа неймспейсов.
5. Ограничитель ресурсов `--uc-max-namespaces` (или `ComposeConfig.parallel_env_limit`
   в новом смысле): если план требует больше неймспейсов, чем разрешено, —
   уменьшить фактическое число воркеров и сообщить об этом в preamble отчёта.
6. Все повторы одного `unique_id` (`--repeat`/`--reruns`) — в один воркер.

Семантика `parallel_env_limit` уточняется и документируется:
сейчас это «сколько разных env-шаблонов можно держать одновременно», в новой
модели — «верхняя граница одновременно живых неймспейсов». Старое поведение при
`parallel_env_limit=1` и без `--uc-parallel` сохраняется без изменений.

## 8. CLI и конфигурация (черновик)

Параллельный плагин (generic):

- `--parallel=N` / алиас `--uc-parallel=N` (N ≤ 1 → плагин прозрачен);
- `--parallel-balance=group-affinity|even`;
- `--parallel-output=live|grouped`;
- защита от рекурсии: если `UC_WORKER_ID` задан — раннер не регистрируется.

Env-плагин (uber-compose):

- `--uc-max-namespaces=K`;
- `--uc-fr-all` (форс-рестарт включая SINGLETON);
- `ComposeConfig`: `parallel_env_limit` (уточнённая семантика),
  `up_concurrency`, опционально `singleton_services`.

`vedro.cfg.py` пользователя:

```python
class Plugins(vedro.Config.Plugins):
    class UberCompose(VedroUberCompose):
        enabled = True
        compose_cfgs = {...}

    class UberComposeParallel(VedroUberComposeParallel):
        enabled = True
        grouping_key = env_group_key   # из uber_compose
```

## 9. Отчётность

Полностью по `03a`/`03b`: воркеры запускаются с `--reporter json`, родитель
построчно читает NDJSON, ретранслирует события в свой `Dispatcher`, собирает
штатный `Report`. Ограничение по traceback (синтетический `ExcInfo`, без живых
фреймов) фиксируется в README.

Дополнительно для uber-compose: в `CleanupEvent` добавлять сводку
«worker → namespaces → сценарии», чтобы падение можно было воспроизвести одним
`vedro run <файл> --uc-...` без параллелизма.

## 10. Деградация и обратная совместимость

### 10.1 Что происходит с `env_id`, когда параллелизм выключен

**Идентификатора потока в `env_id` не появляется.** Слот участвует в имени
только тогда, когда воркеров реально больше одного:

| Режим | Условие | `env_id` | Лейбл `WORKER_SLOT` |
|---|---|---|---|
| Последовательный, один env | `--parallel` нет (или `N<=1`) и `parallel_env_limit == 1` | `default_env_id` (как сейчас) | `-` |
| Последовательный, несколько env | `--parallel` нет и `parallel_env_limit > 1` | `uuid4()[:4]` как сейчас (или детерминированный `{hash4(template)}` без префикса слота) | `-` |
| Параллельный | `--parallel=N`, `N>1` | `w{slot}-{hash4(template)}` | `{slot}` |

Схема именования: `env_id = [w{slot}-] + <id шаблона>`, где префикс слота
добавляется **только** в параллельном режиме. Имена сервисов
(`service-{env_id}`), пути `/tmp/uc-envs/<env_id>/` и ожидания существующих e2e
(`/tmp/uc-envs/default_env_id/...`) в последовательном режиме не меняются.

Следствие: окружения последовательного и параллельного прогонов **не
переиспользуют друг друга** — осознанный компромисс (иначе неймспейс слота 0
пришлось бы считать эквивалентным дефолтному, что конфликтует с `down` чужого
в последовательном режиме).

### 10.2 Совместимость лейблов

Схема лейблов в e2e (`tests/schemas/labels.py`) открытая (`...: ...`), поэтому
добавление `WORKER_SLOT/NAMESPACE/RUN_ID` не ломает существующие проверки;
схему стоит дополнить новыми ключами явно. Матчинг переиспользуемого окружения
должен считать отсутствующий `WORKER_SLOT` эквивалентным `-`, чтобы окружения,
поднятые предыдущей версией uber-compose, продолжали подхватываться.

### 10.3 Остальные гарантии

- Без `--parallel` оба плагина ведут себя идентично текущему: `worker_id=0`,
  `is_parallel_worker()=False`, ап на `StartupEvent` в том же процессе,
  `down` чужих сервисов при `parallel_env_limit=1`.
- Все изменения ядра (singleton, фильтр health, плейсхолдеры) обязаны сохранять
  текущие имена и лейблы при последовательном прогоне — иначе ломаются
  существующие e2e (например, `800_vedro_plugin/110_*`).

## 11. Риски и открытые вопросы

1. **Ресурсы локальной машины** — N воркеров × M env-шаблонов контейнеров.
   Митигация: `group-affinity` + `--uc-max-namespaces` + пре-ап с семафором.
2. **Длина имён контейнеров** при `service-w{slot}-{hash}` — проверить лимиты.
3. **Порты**: неймспейсные сервисы не должны публиковать фиксированные хост-порты.
   Нужна политика: либо `ports` вычищается для неймспейсных сервисов, либо
   публикация только для SINGLETON. Требует решения до реализации.
4. **Уборка**: кто и когда гасит неймспейсы (в конце прогона / по `RUN_ID` /
   отдельная команда `uc down --run-id`). Нужен явный жизненный цикл.
5. **Общая инфраструктура и «грязные» тесты**: тест, ломающий состояние
   SINGLETON (truncate, DDL), влияет на все воркеры. Нужен маркер сценария
   «требует эксклюзивный доступ» → такие сценарии выполняются вне параллели
   (или в отдельной группе с `parallel=1`).
6. **Deprecated `Registry.ScenarioRunner`** — зафиксировать верхнюю границу
   версии vedro в зависимостях.
7. **Флапы health-ожидания** при соседних стартующих неймспейсах — снимается
   фильтрацией по `ENV_ID` (B3), но требует отдельной e2e-проверки.

## 12. Этапы реализации (порядок, каждый проверяется e2e)

| Этап | Содержание | Проверка |
|---|---|---|
| E0 | Лейблы `WORKER_SLOT/NAMESPACE/RUN_ID`; матчинг окружения с учётом слота (B1) | Существующие `tests/scenarios/100_up`, `300_reup` — без регрессий |
| E1 | Реализация `ServiceMode.SINGLETON` в `get_service_map`/`patch_services_names`, shared-namespace, миграции один раз (B4, B8) | Новый e2e: singleton не переименовывается, поднят один раз, доступен из двух неймспейсов |
| E2 | Фильтрация health-ожидания по своему неймспейсу + shared (B3) | Новый e2e: подъём второго неймспейса при «сломанном» соседе |
| E3 | Плейсхолдеры `[[worker_id]]/[[namespace]]/[[env_id]]` в `patch_envs`/`setup_env_for_tests` | Новый e2e на подстановки |
| E4 | Режим «не гасить чужое» + пре-ап нескольких неймспейсов с семафором (B2, B9) | Новый e2e: два неймспейса одного шаблона живут одновременно |
| E4b | Режим **attach-only** в env-плагине (`UC_WORKER_ID` задан → не апать, только резолвить неймспейс и выставлять env) + политика `missing_namespace=fail\|lazy-up` | Новый e2e: воркер прикрепляется к поднятому родителем неймспейсу и не вызывает `docker compose up` |
| E5 | `parallel_plugin`: config/plugin/grouper/worker_filter/worker_api + публикация плана (`set/get_execution_plan`, §5.0.1) — последовательный прогон с корректным `worker_id` | Юнит/e2e на партиционирование, `scheduler.ignore` и порядок обработчиков `StartupEvent` |
| E6 | `runner.py` + `reconstructor.py`: подпроцессы, NDJSON, ретрансляция событий, `Report` | e2e: `--parallel=2` даёт тот же состав результатов, что последовательный прогон |
| E7 | Балансировка, `--uc-max-namespaces`, сводка в отчёте, документация (`docs/`), уборка неймспейсов | e2e + обновление `docs/UBER_COMPOSE_VEDRO_CONFIG.md`, `docs/CLI_USAGE.md` |

E0–E4 полезны сами по себе (без параллелизма) и не ломают текущее поведение —
их можно вести независимо от E5–E7.

## 13. Итог

- Параллелизм строится **на уже существующем механизме `env_id`-неймспейсов**;
  принципиально нового слоя изоляции не требуется.
- **Все окружения поднимает родительский процесс** по плану от параллельного
  плагина, до старта воркеров; воркеры работают в режиме attach-only и
  `docker compose up` не вызывают.
- **При выключенном параллелизме `env_id` не меняется**: остаётся
  `default_env_id` / текущий короткий id, без идентификатора потока; префикс
  `w{slot}-` появляется только при `--parallel>1`.
- Оркестрация — **отдельный плагин** `parallel_plugin` в том же пакете,
  связанный с env-плагином только через env-переменные, `grouping_key` и
  публикацию плана.
- Общая инфраструктура — через доведение до рабочего состояния уже объявленного
  `ServiceMode.SINGLETON` + логическая изоляция плейсхолдерами.
- Перед оркестратором обязательно закрыть блокеры B1–B4 и B8–B9 в ядре, иначе
  параллельный прогон будет нестабильным независимо от качества плагина.
